# 通用插件内核实现规范

本目录固定通用插件内核的架构、公开接口、实现顺序和验收标准。内核实现位于 core/src，公开入口是 core/src/index.ts；运行用例、类型夹具和资源回收检查都放在 core/src 的 __test__ 目录。

core 是与业务无关的 Context 插件宿主。应用通过插件定义服务、调用链、决策关口和通知事件，再组合成 Agent 或其他应用。

## 固定决策

1. 保留 Context 风格的 `apply(ctx)`、`provide/use`、`on/dispatch/emit` 和作用域机制。
2. core 不包含 Agent、会话、对话、模型、工具、房间、Bot、skill、压缩、权限规则和沙箱实现。
3. 持久化、业务状态投影、检查点、恢复和可靠消息投递全部是外部插件的职责。
4. core 管理自己的内存注册表、插件实例、调用、任务和资源生命周期，不恢复 JavaScript 执行栈。
5. 服务消费者取得固定实例的受管门面，不取得提供者的原始实现对象。
6. 服务方法统一返回 `Promise<Result>`；它们可以接收进程内对象，不强制 RPC、JSON 或跨进程序列化。
7. 通知事件、处理调用链和决策关口分别定义语义，不共用含义模糊的回调包装器。
8. 插件可以使用调用链短路和顺序重试；core 限制并发、迟到调用、深度、预算和取消。
9. 插件能请求关闭，宿主负责等待关闭；没有等待自身卸载的插件接口。
10. 安装批次先暂存再发布；回滚保证注册与资源管理，不声称撤销任意外部副作用。
11. 数据错误、状态冲突、缺失依赖和资源上限通过判别联合报告，不能抛业务异常。
12. 测试按行为、不变量和故障场景验收。覆盖率作为遗漏诊断，不能作为提高测试数量的替代目标。

## 使用与验证

插件通过 `apply(ctx)` 登记服务、处理器和资源；宿主通过 `createContext`、`load`、`unload` 和 `dispose` 管理其生命周期。插件拿到固定依赖门面，业务调用的嵌套依赖通过 `call.bind(ctx)` 关联取消和截止时间。具体写法见插件示例。

在本目录执行：

```sh
bun run typecheck
bun run lint
bun run build
bun run test
```

typecheck 包括公开入口正例、18 个编译负例和文档插件示例；lint 包括类型感知检查和纯内核依赖边界；test 在 Bun 下运行并生成覆盖率诊断。测试组织及具体异常矩阵见 [测试说明](core/src/__test__/README.md)。

core 是进程内插件宿主。npm 包获取、模块导入、配置审批与执行隔离由外部宿主提供；已导入插件的在线装配和卸载由 core 提供。通知事件使用内存队列，可靠投递与业务持久化由外部插件提供。
