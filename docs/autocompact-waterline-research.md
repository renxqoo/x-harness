# autocompact 水位线研究报告与改进方案

数据源：`/Users/wrr/.pai/agent/sessions` 全量 2143 个会话，其中 1309 个含 LLM 请求，共 75,891 次请求。分析对象是 autocompact 四阶段（CP 账本、L1 清道夫、L2 真压缩、预算预测）的水位线配置是否合理，以及基于真实负载数据的改进方案。

## 摘要

现行水位线让 1M 窗口的会话在速率最差的区间运行。900k 以上的请求速率只有 4.9 tok/s，是 100k 区间的十分之一。78% 的 L2 线加上测量滞后，实际触发点在 76.9 万到 95 万 token，正好落进速率悬崖。建议 1M 档 L2 从 78 降到 68，配合四项机制改进：可清工具名单扩容、L1 无收益时提前触发 L2、CP 水位与 L2 联动、L2 线引入单步预测。前两项各改一行，收益最大。

## 1. 数据集与方法

每个会话流式解析 `events.jsonl`，提取字段：

| 事件 | 提取内容 | 用途 |
|---|---|---|
| `request/context` | contextWindow、provider、model | 分组口径 |
| `assistant/message` | `usage.input`（含 cacheRead，等于每次请求的全上下文体积） | 占用与速率测量 |
| `assistant/attempt.error`、`llm/retry` | 失败事件与错误码 | 失败率 |
| `surfaceOp: replace` 事件 | user/message（L2 吞段）与 tool/result（L1 占位） | 触发点定位 |
| `autocompact/checkpoint` | CP 落账 | CP 触发点 |
| `compaction/diagnostic` | gate 决策码 | L1/L2 行为复盘 |

两个口径说明。时延用相邻 assistant 消息的间隔做代理，包含工具执行时间，所以用产出速率（output token / 秒）而非绝对延迟来比较桶间差异。失败归属按失败时刻该会话最近一次的 input 所在桶。

## 2. 核心发现

### 2.1 上下文规模对速率的影响

| input 桶 | 请求数 | 产出速率 (tok/s) | 相对 100k 区间 |
|---|---|---|---|
| 0-100k | 27,878 | 49.0 | 1.0x |
| 100-200k | 17,704 | 38.0 | 0.78x |
| 200-300k | 10,292 | 21.7 | 0.44x |
| 300-400k | 6,920 | 18.7 | 0.38x |
| 400-500k | 5,087 | 17.9 | 0.37x |
| 500-600k | 3,849 | 17.0 | 0.35x |
| 600-700k | 2,359 | 14.2 | 0.29x |
| 700-800k | 1,187 | 10.0 | 0.20x |
| 800-900k | 415 | 9.2 | 0.19x |
| 900k+ | 200 | 4.9 | 0.10x |

拐点有两处。200k 处第一次跳水（49 到 21.7），700k 处第二次（14.2 到 10.0，再到 4.9）。900k 以上的每个请求比 100k 区间多花 30 到 40 秒，一个 20 步任务累计多等 10 分钟以上。

### 2.2 失败率

原始失败率在 0-100k 桶高达 12.17%，剔除后降到 5.02%。被剔除的 3,278 个事件来自 500 个会话的配置性失败，其中 `no-adapter` 751 次（空 key 档案，本次事故根因）、`non-retryable` 1,253 次（认证与内容审查）。按 provider 分解 0-100k 桶的原始失败率：字节云 52.89%、MiniMax 43.27%、小写 glm 19.78%、大写 GLM 7.51%。这批失败与上下文大小无关，是坏档案问题，已由先前的修复处理。

剔除配置性失败后的真实失败率：

| input 桶 | 失败率 | | input 桶 | 失败率 |
|---|---|---|---|---|
| 0-100k | 5.02% | | 500-600k | 1.58% |
| 100-200k | 1.81% | | 600-700k | 0.68% |
| 200-300k | 2.54% | | 700-800k | 0.76% |
| 300-400k | 4.64% | | 800-900k | 3.86% |
| 400-500k | 5.15% | | 900k+ | 2.00% |

失败率没有随上下文单调上升。300k 到 500k 有一个 5% 左右的峰（429/503 集中），700k 以上反而低，因为能跑到那么大的会话用的都是 GLM 主力通道。按天看，10-04（22.92%）和 10-12（18.08%）是 provider 故障日。结论：失败率不是大上下文的主要代价，速率才是。

### 2.3 水位线执行偏移

配置线与实测触发点的对照（L2 真压缩）：

| 会话 | 窗口 | 配置线 (78%/72%) | 实际触发 | 偏移 | 压缩后 | 收益 |
|---|---|---|---|---|---|---|
| cmxidv | 1M | 764k | 950k | +186k | 407k | -57% |
| 5w75d6 | 1M | 764k | 769k ×4 | +5k | 306k / 574k | -60% / -25% |
| pje5gk | 128k | 77k（净） | 82k | 贴合 | 未记录 | - |

偏移来源是测量粒度。占用只在每步开始的 gate 测量（`packages/autocompact/src/gate.ts:114` `runStepGate`），长工具回合内单步可涨几十 k token，越线后要等下一步的 gate 才拦截。cmxidv 的 +186k 说明单个回合的增量可以达到这个量级。压缩效果本身健康，95 万压到 40.7 万。

CP 线没有偏移问题。1M 会话 CP 首次落账的中位 input 是 296k，配置线 294k（30%），基本贴合。

### 2.4 触发率与成本

329 个 1M 窗口会话的统计：

| 指标 | 数值 |
|---|---|
| max_input 中位 / p90 / p99 | 82k / 273k / 769k |
| 触发过 L2 的会话 | 3 个（1%） |
| 达到窗口 85% 以上的会话 | 1 个 |
| CP 成功过的会话 | 11 个（3%） |
| L1 平均清理次数（全会话均值） | 84 次 |

99% 的会话终生不需要 L2，但 CP 的 30% 水位让每个跨过 29.4 万的会话都开始发账本请求。按每笔 CP 请求约 20 秒 flash 调用计，对一个峰值 30 万 token 的普通会话，这套机制只产生成本不产生收益。

### 2.5 L1 失效结构（mrod40 案例）

mrod40 卡在 70.7 万 token，L1 报 `l1-no-gain {gainTokens: 0}`。用生产代码对该会话 journal 复放当时的 `computeClearPlan`，结果：可清工具（read/grep/bash）只剩 5 条 bash 共 1,312 token，全部落在 `clearKeepRecent: 5` 的保窗内，切片后收益为零。该会话历史清理 1,754 次，能清的早清完。

剩余未清工具结果的构成（不在 `clearableTools` 名单内）：

| 工具 | 未清 token | | 工具 | 未清 token |
|---|---|---|---|---|
| edit | 15,999 | | write | 1,007 |
| task_update | 5,982 | | agent_message | 738 |
| agent_spawn | 1,760 | | task_create | 345 |
| list_agents | 1,664 | | bash（保窗内） | 1,312 |

`clearableTools` 默认只有 `["read", "grep", "bash"]`（`packages/autocompact/src/plugin.ts:49`）。列表型输出（task_update、task_create、list_agents）替换成占位符没有信息损失，却在名单外。edit 和 write 的 diff 原文是主要残留，占未清量的 54%。

### 2.6 四阶段机制回顾

上下文不是 journal 本身，是 journal 按 `surfaceOp` 重放折叠出的投影（`packages/core/session/src/surface.ts:36` `projectSurface`）。一个阶段的动作落成 replace 事件的那一刻，下一个请求（`packages/agent-loop/src/step.ts:119` `session.deriveMessages()`）就用到新上下文。

| 阶段 | 水位（1M 档） | 动作 | 生效时机 |
|---|---|---|---|
| CP 账本 | 30% (294k) | 后台请求 flash 模型把已过轮次折叠进 ledger | 不改变上下文，旁路记账，是 L2 的前置弹药 |
| L1 清道夫 | 55% (539k) | 把旧 tool/result 原文替换成 `[cleared: ...]` 占位符 | 落 journal 即刻生效 |
| L2 真压缩 | 78% (764k) | 用账本正文加文件清单合成一条 user/message，一次性吞掉锚点到切点的整段历史 | 落 journal 即刻生效，唯一真正瘦身的动作 |
| 预算预测 | warn 线 | 单步增量预测将爆窗口时提前触发 L2 或 join | 同 L2 |

L2 触发时若 CP 在飞会先 `joinInflight` 等待（上限 120s）；账本未就绪时发 `budget-gate-release {ledger-unready}` 放行本轮，这是本次事故中真压缩路径被锁死的直接机制。

## 3. 水位线建议

现行配置与建议对照（cp/l1/l2 为 effectiveWindow 百分比，effectiveWindow = contextWindow − min(maxOutputTokens, 20k)）：

| 窗口档 | 现行 | 建议 | 依据 |
|---|---|---|---|
| ≤300k | 40/50/72 | 45/60/75 | 200k 处速率已从 49 跌到 21.7。L1 提前到 60% 让清道夫在速率跳水前先跑一轮。L2 从 72 提到 75 是因为 300k 以下窗口本身小，压缩过早会频繁丢上下文 |
| ≤700k | 35/55/75 | 35/55/70 | 500k 失败率峰 5.15%。L2 从 75 提前到 70，让会话在进入 600k+ 低速区之前完成压缩 |
| 1M | 30/55/78 | 30/50/68 | 700k 是速率第二拐点（14.2 到 10.0）。68% = 66.6 万，加上实测的测量滞后（最大 +186k，典型 +5k），实际触发在 67 万到 70 万，压完回到 30 万附近。现行 78% 的实际触发是 77 万到 95 万，整个落在悬崖里 |

设计原则：L2 线设在「速率第二拐点减去典型测量滞后」的位置，而不是「窗口减去安全余量」。速率数据是主要约束，失败率数据只作为 500k 档的修正输入。

## 4. 机制改进方案

按收益排序。

### 改进 1：clearableTools 扩容（一行，最高优先）

`packages/autocompact/src/plugin.ts:49` 的默认名单加入 `task_update`、`task_create`、`list_agents`。这三个是列表型输出，占位符化后模型仍能从后续对话获得状态。mrod40 案例中它们合计约 8 千 token，是保窗外可立即回收的部分。

`edit` 与 `write` 的 diff 结果（mrod40 中 1.7 万 token）做截断而非全文保留：结果超过 `toolResultCapTokens`（现配置 25k）时保留头部 N 行加尾注。截断比占位符保守，因为 diff 承载「改了什么」的记忆。

### 改进 2：L1-L2 死区联动（小改）

现状：`l1-no-gain` 后设置 `l1Backoff`，本 turn 不再尝试 L1，但要干等到 78% 的 L2 线才压缩。mrod40 在 53.9 万（l1 线）到 76.4 万（l2 线）之间空转了整个后半程，这段区间正好覆盖速率从 17 到 10 的恶化带。

改法：`gate.ts` 的 `l1AndBeyond` 里，`l1-no-gain` 且 remeasure 后 occupancy 超过 l1 线 15 个百分点时，直接调 `escalateOrJoin`。死区从 23 个百分点收窄到 15 个以内。账本就绪时立即压缩，未就绪时走现有的 join 路径。

### 改进 3：CP 水位与 L2 联动（一行）

CP 账本的价值只在 L2 触发时兑现，而 99% 的会话到不了 L2。建议 cp 水位从各档固定值改为 `l2 - 25` 个百分点（1M 档即 68 − 25 = 43%，300k 档即 75 − 25 = 50%）。账本在真正需要前约 25 个百分点的窗口内就绪即可，一次 CP 请求约 20 秒，25% 窗口的增长时间远大于此。短会话不再付无用的账本请求。

### 改进 4：L2 线单步预测（中改）

`budgetOverflowPredicted` 已经为 L1 区间做了单步增量预测（`gate.ts` 的 `routeZones`），但 L2 线没有享受同样待遇。把该预测同样应用在 l2 线：预测下一步将越线即提前触发 `escalateOrJoin`。这直接消除 cmxidv 式的 +186k 偏移，也是对改进 2 的泛化。

### 改进 5：窗口配置校验（防御）

3 个 09-29 的会话 input 达到声明窗口的 150% 到 223%（128k 假窗口时期的产物），静默跑完。建议在 gate 里加一条：实测 usage 锚超过声明窗口时发 `lines-degraded` 类告警并按实测值收缩 effectiveWindow。同类配置错误（空 key 档案）藏了 3 天才被找到，超窗也应该有可见信号。

## 6. 未验证假设与回滚口径

68% 的 L2 线在真实负载下可能偶发过早触发（会话还在活跃增长时就压缩）。观测一个周期后若发现压缩后 10 万 token 内再次触顶，上调 3 到 5 个百分点。同样，`clearableTools` 扩容后如果发现模型频繁追问任务状态，把 `task_update` 移回名单外。

本报告的全部数字来自既有 journal 的离线分析，未做在线实验。改进 1、2、3 的效果可以用下一个自然产生的长会话直接检验，不需要专门构造负载。
